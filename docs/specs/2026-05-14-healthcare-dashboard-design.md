## 1. Purpose & scope

Build a patient-management dashboard for a small medical practice. The app must demonstrate full-stack judgment, not feature breadth — every choice should read as deliberate to a reviewer skimming the repo.

In scope (this spec):

- React (TypeScript) frontend, FastAPI backend, PostgreSQL database
- All five parts of the take-home brief (foundation, core dashboard, notes, forms, containerization)
- A curated subset of stretch goals: Alembic migrations, list sort/filter query parameters, list virtualization, dark/light theme, backend + frontend unit tests, GitHub Actions CI
- Documentation: this spec, ADRs for major decisions, one HLD diagram, one step-by-step manual, a README
- Kubernetes-equivalence story expressed as a `k8s/` manifest folder + ADR, with the runtime dev loop on Docker Compose `develop.watch`

Out of scope:

- Authentication / multi-tenant data isolation (single-practice assumption)
- Real PHI handling / HIPAA compliance work
- Real-time collaboration (notes are CRUD, not live-edited)
- Mobile-native client
- E2E tests (Pytest + Vitest only)
- Memoization "theater" (memoize where a profiler says so, not by default)

## 2. Success criteria

A reviewer can:

1. `git clone` the repo, copy `.env.example` to `.env`, run `docker compose up`, and see the dashboard at `http://localhost:5173` within ~2 minutes of starting the pull.
2. See a patient list seeded with 20 patients, search/filter/sort it, open a patient, add and delete notes, and view a generated summary.
3. Create and edit a patient with both client- and server-side validation visible.
4. Read `README.md` and understand the architecture, the trade-offs, and how to run + extend the system.
5. Read the ADRs and HLD and form an opinion about the decisions without needing to ask questions.
6. Read `k8s/README.md` and understand how the Compose topology maps to Kubernetes primitives.

## 3. Tech stack (locked)

### Frontend
- **Build:** Vite + React 18 + TypeScript (strict)
- **Routing:** React Router v6 (`createBrowserRouter`, data router APIs)
- **Server state:** TanStack Query v5
- **Client UI state:** Zustand (theme, sidebar collapse — anything not server-derived)
- **Forms:** React Hook Form + Zod (schema imported from a shared `schemas` module)
- **API client:** `openapi-typescript` codegen from FastAPI's `/openapi.json` → thin typed `fetch` wrapper
- **Styling:** Tailwind CSS + shadcn/ui (Radix primitives) + lucide-react icons
- **Typography:** Inter (body), Instrument Serif (display), JetBrains Mono (timestamps/MRN/kbd)
- **Virtualization:** TanStack Virtual for patient list when row count > 50
- **Tooling:** ESLint, Prettier, TypeScript strict, Vitest + React Testing Library

### Backend
- **Framework:** FastAPI (Python 3.12)
- **DB:** PostgreSQL 16
- **ORM / models:** SQLAlchemy 2.x + Pydantic v2 (separate `models/` for SQLAlchemy and `schemas/` for Pydantic)
- **Migrations:** Alembic, autogenerated then hand-edited
- **Seeding:** idempotent Python seed script invoked from the container entrypoint after migrations run
- **Summarizer:** abstract `Summarizer` interface with two implementations — `TemplateSummarizer` (default) and `ClaudeSummarizer` (used when `ANTHROPIC_API_KEY` is set)
- **Testing:** Pytest + `httpx.AsyncClient` against a disposable Postgres container (testcontainers) or an in-memory SQLite fallback for fast unit tests of pure logic

### Infrastructure
- **Local dev:** Docker Compose with `develop.watch` for hot-reload on both apps
- **K8s parity:** `k8s/` folder with `Deployment`, `Service`, `ConfigMap`, `Secret`, `PersistentVolumeClaim` manifests. Not used at runtime — exists to document the topology and prove the apps are 12-factor.
- **CI:** GitHub Actions, two parallel jobs (frontend, backend), each running lint + typecheck + test + build.

## 4. Domain model

Two entities. Names are deliberately boring to keep the focus on the system, not the data.

### `Patient`

| field         | type                              | constraints                              |
|---------------|-----------------------------------|------------------------------------------|
| `id`          | UUID                              | primary key                              |
| `first_name`  | string                            | required, 1–80 chars                     |
| `last_name`   | string                            | required, 1–80 chars                     |
| `date_of_birth` | date                            | required, must be in the past            |
| `phone`       | string                            | required, E.164-shaped (validated)       |
| `email`       | string \| null                    | optional, RFC-valid if present           |
| `address`     | string \| null                    | optional, ≤ 240 chars                    |
| `blood_type`  | enum (`O+`,`O-`,`A+`,`A-`,`B+`,`B-`,`AB+`,`AB-`) | required                  |
| `status`      | enum (`active`,`follow_up`,`inactive`) | required, default `active`          |
| `conditions`  | string[]                          | stored as `text[]`, default `[]`         |
| `allergies`   | string[]                          | stored as `text[]`, default `[]`         |
| `last_visit_at` | timestamptz \| null             | nullable; updated implicitly when a note is added |
| `created_at`  | timestamptz                       | default `now()`                          |
| `updated_at`  | timestamptz                       | default `now()`, auto-updated            |

Derived fields surfaced via API but not stored:
- `age` — computed from `date_of_birth`
- `mrn` — formatted from `id` as `MRN-{first 5 of UUID hex}`

### `Note`

| field        | type        | constraints                                  |
|--------------|-------------|----------------------------------------------|
| `id`         | UUID        | primary key                                  |
| `patient_id` | UUID        | FK → `patients.id`, ON DELETE CASCADE        |
| `content`    | text        | required, 1–4000 chars                       |
| `author`     | string      | required, free-text (no user table yet)      |
| `created_at` | timestamptz | default `now()`; client may pass a timestamp |

Indexes:
- `patients(last_name, first_name)` — list sort default
- `patients(status)` — pill filter
- `notes(patient_id, created_at DESC)` — note list

## 5. API surface

All routes under `/api/v1`. JSON only. Errors use FastAPI's `HTTPException` mapped to a shared envelope `{ "detail": "...", "errors"?: [{...}] }`.

```
GET    /health                              → {"status":"ok"}
GET    /patients                            → paginated list
        ?page=1&page_size=20
        &search=marisol
        &status=active|follow_up|inactive
        &sort=last_visit_at|name|created_at
        &order=asc|desc
GET    /patients/{id}                       → single patient
POST   /patients                            → create
PUT    /patients/{id}                       → full replacement
DELETE /patients/{id}                       → 204, cascades notes

GET    /patients/{id}/notes                 → list, newest first
POST   /patients/{id}/notes                 → create
DELETE /patients/{id}/notes/{note_id}       → 204

GET    /patients/{id}/summary               → { summary: string, source: "template"|"claude", note_count: number }
```

Pagination response envelope:

```jsonc
{
  "items": [ /* Patient */ ],
  "page": 1,
  "page_size": 20,
  "total": 142,
  "total_pages": 8
}
```

HTTP status conventions:
- `200` reads, `201` create, `204` delete, `400` validation, `404` not found, `409` conflict (reserved), `422` Pydantic validation, `500` unexpected.
- Validation errors return `422` with a per-field `errors` array (Pydantic's default, slightly normalized).

Two clear seams:
- **Routers ↔ services** — routers handle HTTP shape; services contain logic. Easy to unit-test services.
- **Features ↔ shared** — frontend features own their routes, hooks, components, and Zod schemas. Shared UI primitives live in `components/ui`.

### 6.2 Data flow (read path)

```
Browser → React Router loader-less route
       → useQuery(['patients', filters])
       → fetch /api/v1/patients?... (typed via openapi-typescript)
       → FastAPI router
       → patients service (SQLAlchemy)
       → Postgres
```

### 6.3 Data flow (summary)

```
GET /patients/{id}/summary
   → SummaryService.build(patient, notes)
   → Summarizer (interface)
       ├── TemplateSummarizer  (default)
       └── ClaudeSummarizer    (if ANTHROPIC_API_KEY)
   → returns { summary, source, note_count }
```

The summarizer is constructed once at app startup based on settings, then injected via FastAPI `Depends`. Switching implementations requires no router changes.

## 7. Frontend behaviors

### 7.1 Patient list
- Default sort: `last_visit_at desc, last_name asc`.
- Search debounced to 250ms; sent as `?search=`.
- Status filter via pill row, single-select; "All" sends no `status` param.
- Sortable column headers send `sort` + `order`.
- Pagination footer when total > page_size; switches to TanStack Virtual when current page holds > 50 rows (configurable via constant).
- Loading state: 6 skeleton rows. Empty state: serif copy + CTA.

### 7.2 Patient detail
- Three async resources fetched in parallel via React Query: `patient`, `notes`, `summary`.
- Summary is its own query, invalidated when notes are mutated.
- Notes composer is a controlled `<textarea>` with optimistic insert; failure rolls back and surfaces a toast.
- Delete patient is a confirm dialog (Radix) — typing the last name to confirm. Cascade is explicit in copy.

### 7.3 Patient form
- One Zod schema shared by create and edit. `mode: "onBlur"`, `reValidateMode: "onChange"`.
- Phone field validated as E.164-ish (`/^\+?[0-9 .()-]{7,20}$/`); server has the authoritative rule.
- Server-side 422 errors mapped back into RHF field errors by `loc[-1]` path.
- Submit button disabled while pending; full network failures shown as a top-of-form banner with retry.

### 7.4 Theme
- Default to system preference, persisted to `localStorage` via Zustand.
- CSS variables in `:root[data-theme]` (matches the mockups exactly so the design carries over).
- Toggle lives in the sidebar footer.

### 7.5 Virtualization
- TanStack Virtual on the patient list `<tbody>` when row count exceeds 50 (per-page rendering still hits the API).
- Row height fixed (56px) to avoid measurement passes.

### 7.6 Code splitting
- Each route is a lazy chunk via `React.lazy` + `Suspense`. Initial bundle excludes patient form and detail.

## 8. Backend behaviors

### 8.1 Validation
- Pydantic v2 schemas with `Field` constraints (lengths, regex, enums).
- Custom validator for `date_of_birth` (must be past).
- 422 envelope is preserved from FastAPI defaults; documented in OpenAPI.

### 8.2 Sorting/filtering
- `sort` whitelisted to a fixed set; unknown values → 400.
- `search` matches `first_name`, `last_name`, and MRN suffix using `ILIKE` with a leading-wildcard substring. (Acceptable at this scale; ADR notes the trade-off vs `pg_trgm`.)

### 8.3 Seeding
- 20 patients with realistic names spanning ages, blood types, and statuses.
- 3–8 notes per patient, timestamps spread over the last 90 days.
- Seed is idempotent: it counts patients first and exits if `>= 20`.

### 8.4 Summarizer

**Template implementation** (default):
> {first_name} {last_name} is a {age}-year-old, blood type {blood_type}. Status: {status}. Active conditions: {conditions or "none recorded"}. Allergies: {allergies or "none recorded"}. {note_count} clinical notes on record; the most recent ({recent_date}) reads: "{first 180 chars of latest note}".

**Claude implementation:**
- Uses `claude-haiku-4-5-20251001` for speed and cost.
- Prompt-cached system prompt (clinician-style guidance).
- Bounded output (≤ 250 tokens).
- Times out at 8s and falls back to template, logging the failure.

### 8.5 Logging
- Structlog-style JSON request logs in production, pretty in dev. Not a stretch goal — needed for the K8s ADR to claim 12-factor.

## 9. Errors and edge cases

| case                                            | behavior                                                      |
|-------------------------------------------------|---------------------------------------------------------------|
| Patient not found                               | 404, `{ detail: "Patient not found" }`                        |
| Note not found (or wrong patient)               | 404                                                           |
| Validation failure                              | 422 with per-field errors                                     |
| Sort param outside whitelist                    | 400                                                           |
| Page out of range                               | Empty `items`, correct `page`/`total`                         |
| Summarizer fails (network/timeout/parse)        | Fall back to template, log warning, still 200                 |
| Database down on startup                        | API fails health check until reachable; entrypoint retries 30× |
| Concurrent update (lost-write)                  | Out of scope — last-write-wins, called out in ADR             |

## 10. Testing strategy

**Backend (Pytest):**
- Endpoint tests: list pagination, sort/filter, CRUD happy paths, validation 422, 404s.
- Service tests: template summarizer formatting; seed idempotency.
- Skipped/marked: ClaudeSummarizer (requires key, ran ad-hoc).

**Frontend (Vitest + RTL):**
- Patient form: required-field errors, server-422 mapping, submit success.
- Patient list: filter pill changes URL params, search debounces.
- Summary panel: renders provided text, shows the "source" badge.

No E2E. The README explicitly states this is a known gap.

## 11. CI

`.github/workflows/ci.yml`, two parallel jobs:
- `web`: `pnpm install` → `pnpm lint` → `pnpm typecheck` → `pnpm test` → `pnpm build`
- `api`: `uv sync` → `ruff` → `mypy` → `pytest` → `python -m app.main --check`

Both jobs run on PRs and on push to `main`. No deploy step (out of scope).

## 12. Containerization

- `apps/api/Dockerfile`: python:3.12-slim, multi-stage (builder installs deps, final stage copies app). Healthcheck hits `/health`.
- `apps/web/Dockerfile`: node:20-alpine builder → nginx:alpine final stage serving `/dist`. Healthcheck hits `/`.
- `docker-compose.yml`: `db`, `api`, `web` services + a `migrate` one-shot that runs Alembic before `api` starts. `develop.watch` mounts source for hot-reload in dev (`docker compose watch`).
- `.env.example` documents `DATABASE_URL`, `ANTHROPIC_API_KEY` (optional), `VITE_API_URL`, etc.

## 15. Implementation order (preview, not the full plan)

Detailed plan comes from the writing-plans skill. High-level phases:

1. **Foundation** — repo skeleton, Compose, DB up, `/health`, blank Vite app routing to a "hello" page
2. **Patient model + CRUD + seed** — backend complete with tests
3. **Frontend shell + patient list** — sidebar, topbar, list with filter/sort/pagination
4. **Patient detail + notes** — including summary endpoint and panel
5. **Patient form** — create/edit with Zod + RHF + server-error mapping
6. **Polish** — virtualization threshold, theme persistence, error boundaries, empty/loading states
7. **Stretch** — request logging, code splitting confirmation, CI workflow, K8s manifests
8. **Docs** — README, ADRs, HLD diagram, manual

Each phase ends with a green test run.
